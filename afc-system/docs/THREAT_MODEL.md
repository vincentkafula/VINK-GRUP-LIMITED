# Threat model

What the design defends against, how, and what risk is left. "Held" means the property is enforced by the code or the database and tested; "reduced" means mitigated but not eliminated.

| # | Threat | Defence | Left over |
|---|---|---|---|
| 1 | **Cloned UID** (a cheap card or phone copies a card's UID) | The UID is never trusted. The validator authenticates with the card's own AES key; a copied UID cannot answer. Tested (`a card with the right UID but other keys is refused`). Held. | None for the UID itself. |
| 2 | **Full card clone** (an attacker obtains a card's keys and copies the whole card) | Per-card diversified keys: one card's keys reveal nothing about another's. A copy shares its card's tap counter, so two copies tapping offline produce the same counter on the server: flagged `DUPLICATE_COUNTER` (HIGH), the second claim is kept for investigation but **not posted**, three flags block the card. Reduced. | The attacker can spend the card's balance once on each copy before it is detected, so the loss is bounded by the R 5 000 cap per card. Keys can only be read by attacking the card chip or the key store. |
| 3 | **Replay** of a card exchange (recording and resending) | Authentication uses fresh random numbers each time; every command carries a CMAC chained to the previous one, so a recorded debit is meaningless on a new session. Tested (`replaying a recorded debit does nothing`). Held. | None. |
| 4 | **Replay** of a device's report to the server | Each request carries a timestamp (5-minute window), a one-time nonce stored for 10 minutes, and an HMAC over the exact body. The reply is signed too. Each tap also has an id the server stores once. Tested. Held. | A device clock more than 5 minutes wrong cannot sync (by design); fix the clock. |
| 5 | **Forged server reply** (injecting a fake hotlist or fare table) | The device only accepts a reply whose HMAC verifies with its own secret. Tested. Held. | Someone with the device's secret can forge replies to that device. |
| 6 | **Offline double spend** (spending the same balance on two devices) | The balance lives **on the card**, and every debit is an atomic transaction on it, so two devices cannot both spend the same money from one genuine card. The server's books follow the card. A card that was cloned: see 2. Held for genuine cards. | Fare tables and the hotlist are only as fresh as the last sync; a card blocked a minute ago can still be used on a device that has not synced. Keep sync intervals short on busy routes. |
| 7 | **Half-written taps** (card pulled away, power cut) | One DESFire transaction: debit and tap record commit together or not at all. A disk-backed intent resolves an unknown outcome by the card's counter on its next tap. Tested (pulled card, lost reply, restart). Held. | The passenger may have to tap twice; they are never charged twice. |
| 8 | **Tampered or malicious device** | The device can only take money (DEBIT key). It cannot add value. Its reports are checked: arithmetic, a fare ceiling per route, counter continuity, the card's balance against the ledger; HIGH findings block the card. Reduced. | A device that holds the `DEBIT` master key in software can drain any card it can touch, up to the card's balance. Use a SAM so the key never leaves the chip; monitor per-device revenue in the reports. |
| 9 | **Stolen device** | Revoke it in the dashboard (its signing secret stops working immediately; its rotation counter makes the old secret useless). Reduced. | If the master key was in the device's environment, rotate the master and re-key cards, or accept the exposure. This is why a SAM is recommended. |
| 10 | **Server or database compromise** | The ledger cannot be edited by the application, or even by a direct SQL `UPDATE`/`DELETE`/`TRUNCATE` (database triggers). Staff passwords are scrypt hashes. Device secrets are derived, not stored. Master card keys are not on the server at all. Reduced. | Someone with DB superuser rights can drop the triggers: restrict that role, keep backups and ship the audit log elsewhere. `DEVICE_KEY_MASTER` and `JWT_SECRET` are in the server's environment. |
| 11 | **Insider misuse** | Roles (admin, operator, agent, viewer) enforced on every route; operators see only their own routes and money; every change is in the audit log with who and from where; top-ups need a unique reference; manual adjustments are restricted. Reduced. | Admins are trusted. Review the audit log. |
| 12 | **Brute force on staff sign-in** | Per-account lock (5 failures, 15 minutes), per-address rate limit, generic error, constant-time comparison. Tested. Held. | No second factor yet (add one before exposing the dashboard to the internet at scale). |
| 13 | **Forged mobile-money callback** | HMAC signature over the raw body; off unless a secret is set; idempotent on (method, reference). Tested. | The placeholder format is not a real provider's: use the provider's own signing scheme. |
| 14 | **Spreadsheet formula injection** in CSV exports | Cells that start with `= + - @` are neutralised. Tested. Held. | |
| 15 | **Denial of service** | Rate limits (global, sign-in, per device), body size caps, validation on every input. Reduced. | Put a proxy/WAF in front. |
| 17 | **Copied or forged single-trip ticket** (Ultralight) | Tickets carry an Ed25519 signature over their data and the card's UID: forged or altered data, and data copied onto a card with a different UID, fail the check; validators hold only the public key. Writes need a per-card password (locked configuration, five-try lockout). A used ticket is marked on the card, recorded on the device, and the server flags a ticket number used twice (HIGH). Tested. Reduced. | Ultralight has no card-side crypto: a full copy onto a card with the **same UID** (special cards) of an *unused* ticket works once on each device that has not heard of the other use. Keep tickets cheap and short-lived. |
| 18 | **Master keys in plain files or environment variables** | Sealed key files: scrypt + AES-256-GCM, one file per kind of station holding only the roles it needs, role list authenticated; the passphrase comes from a secret store. Tested. Reduced. | While a program runs, the keys are in its memory; a hardware module (SAM/HSM) is the stronger answer. A lost passphrase or lost backup of all.sealed makes cards unusable. |
| 16 | **Privacy** | Taps are stored against the card UID and an optional holder name. Only what is needed is kept. | These are personal data (POPIA): decide retention, access, and a privacy notice. |

## Weak points of this implementation to be aware of

- The card protocol is implemented from NXP's documents and tested against a software card written by the same author, plus published test vectors for the primitives. Run the self-test on real cards before relying on it.
- The EV1-compatible AES channel is used, not EV2/EV3 secure messaging. It is sound but older.
- Staff tokens live in `sessionStorage` (cleared when the tab closes). An XSS bug in the dashboard would expose them; the dashboard has no HTML injection paths today, but keep it that way.
